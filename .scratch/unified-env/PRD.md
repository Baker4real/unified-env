# PRD：本机统一环境治理

Status: done

> 本 PRD 拆分出的 17 个 issue 均已进入终态 `done`。本文保留原始问题、范围和设计约束；当前能力与事实以根目录 `README.md`、`CONTEXT.md` 和重新生成的 `reports/` 为准。

## Problem Statement

本机开发环境分散在多个位置：有些运行时和工具已经在 D 盘，有些工具仍来自 C 盘或用户目录，有些缓存路径已经显式迁到 D 盘，但仍残留默认缓存目录；项目本地 `.venv`、`node_modules` 又有自己的隔离价值，不能被简单合并。

用户真正要解决的问题不是“全机只能有一份环境”，而是让环境状态可见、可复用、可更新、可安全迁移。当前如果直接搬目录或统一环境，风险很高：解释器、shim、PATH、注册表、服务、包管理器缓存、项目本地依赖都可能绑定旧路径或包含不可迁移状态。

## Solution

建立一个本机统一环境治理项目，先用只读盘点建立事实基线，再把环境资产分成可复用、可迁移、人工审查和绝不自动迁移几类。后续迁移必须以 dry-run 计划、显式授权、回滚步骤和验证步骤为前提。

第一阶段交付一个可信的只读盘点器和中文报告。它不移动文件、不修改环境变量、不执行更新，只回答四个问题：

- 本机有哪些开发工具、运行时、缓存和项目本地环境。
- 它们当前位于 C 盘、D 盘还是其他位置。
- 哪些对象可以考虑迁移，哪些必须人工审查。
- 后续迁移或统一更新应该从哪里开始。

## User Stories

1. 作为本机开发者，我想看到当前开发工具和运行时清单，以便知道机器上到底有哪些环境入口。
2. 作为本机开发者，我想看到工具入口所在路径，以便识别哪些仍来自 C 盘或用户目录。
3. 作为本机开发者，我想看到 PATH 入口顺序，以便判断命令冲突和旧 shim 是否会影响后续迁移。
4. 作为本机开发者，我想看到 Python、Node、Rust、.NET、Java、Go 等生态的存在状态，以便决定统一环境优先级。
5. 作为本机开发者，我想看到 uv、pip、npm、pnpm、Cargo、NuGet、Maven、Gradle 等缓存位置，以便优先迁移低风险缓存。
6. 作为本机开发者，我想知道哪些缓存已经配置到 D 盘，以便避免重复迁移和错误回退。
7. 作为本机开发者，我想识别仍在 C 盘的默认缓存目录，以便把它们列为候选而不是直接处理。
8. 作为本机开发者，我想看到项目本地 `.venv`、`node_modules` 等环境标记，以便确认它们不会被误合并。
9. 作为长期服务维护者，我想把服务依赖的项目本地环境标为人工审查项，以便避免破坏正在运行或可恢复性很差的服务。
10. 作为本机开发者，我想明确哪些目录绝不自动迁移，以便避免系统、凭据、服务或 Store/MSI 管理内容被误动。
11. 作为本机开发者，我想让报告区分迁移候选和人工审查项，以便后续 agent 不会把“看到的环境”误解成“可以移动的环境”。
12. 作为本机开发者，我想让盘点器保持只读，以便可以反复运行而不改变机器状态。
13. 作为本机开发者，我想生成机器可读 JSON，以便后续脚本可以基于同一事实基线生成迁移计划。
14. 作为本机开发者，我想生成中文 Markdown 报告，以便自己审查风险、优先级和下一步。
15. 作为后续 agent，我想读取稳定 schema 的 inventory，以便实现迁移计划、更新计划或健康检查时不重新猜测环境结构。
16. 作为后续 agent，我想读取人工审查项，以便在没有明确授权时跳过项目本地环境和高风险对象。
17. 作为后续 agent，我想看到 reparse point / junction / symlink 信息，以便避免路径循环或目标不明造成误迁移。
18. 作为后续 agent，我想知道扫描范围和排除范围，以便理解报告盲区。
19. 作为本机开发者，我想先处理低风险缓存迁移，以便用小步骤验证迁移策略。
20. 作为本机开发者，我想把每次真实迁移拆成独立 issue，以便每一步都有回滚和验证。
21. 作为本机开发者，我想后续统一更新入口，但不希望更新器越权处理敏感目录。
22. 作为本机开发者，我想让工具链复用从实用性出发，以便该共享的共享、该隔离的隔离。

## Implementation Decisions

- 第一阶段只交付只读盘点能力，不包含真实迁移、更新或安装动作。
- 环境资产分成几类：工具入口、环境变量、PATH 入口、已知目录、项目本地环境、迁移候选、人工审查项、绝不自动迁移根。
- 迁移候选只包含可考虑迁移的低风险或中风险对象；项目本地环境、reparse point、凭据/服务相关对象进入人工审查项。
- 项目本地 `.venv`、`node_modules`、`.conda` 默认不自动迁移，因为它们可能绑定解释器、绝对路径、构建产物或运行时状态。
- 默认报告必须明确“本次扫描未移动文件、未修改环境变量、未执行软件更新”。
- 后续迁移必须先生成 dry-run 计划，再执行迁移，并包含回滚和验证步骤。
- 统一环境策略以 D 盘为目标位置，但不强制所有项目依赖合并到一份环境。
- 对官方安装器、Store、MSI、Windows 系统目录、服务目录、凭据目录和数据库/虚拟磁盘状态，不做自动迁移。
- 包管理器和运行时管理器优先使用官方配置或重装方式切换目录，不直接搬动工具根。
- 版本探测必须容错：工具不存在、命令输出异常、编码异常、命令需要交互时，盘点器仍应完成报告。

## Testing Decisions

- 测试优先覆盖外部行为：运行盘点器后能否生成稳定 JSON 和中文报告，而不是测试内部函数实现细节。
- 最高层测试接缝是 CLI 行为：执行盘点命令，验证它完成且输出只读声明。
- 第二个测试接缝是 JSON 契约：读取 inventory，验证核心字段存在且可被后续工具消费。
- 第三个测试接缝是报告内容：验证报告包含只读声明、绝不自动迁移清单、迁移候选和人工审查项。
- 快速模式应可跳过版本探测，避免外部工具调用不稳定时阻塞基础路径扫描。
- 完整模式应能容忍个别工具版本输出失败，不影响整体报告生成。
- 后续每个真实迁移 issue 都必须有独立验证：迁移前后路径检查、工具命令检查、回滚检查。

## Out of Scope

- 不移动任何目录或文件。
- 不创建 junction、symlink 或 reparse point。
- 不修改用户级或机器级环境变量。
- 不修改 PATH。
- 不执行任何软件更新。
- 不安装 `uv`、`mise`、`Scoop`、`topgrade` 或其他工具。
- 不迁移 Windows 系统目录、Program Files、ProgramData、WindowsApps、服务状态、浏览器 profile、证书、SSH/GPG key、token、license 或 DPAPI 保护数据。
- 不把项目本地依赖环境合并成一个全局环境。
- 不替代具体项目自己的依赖管理流程。

## Further Notes

本节是立项时的历史判断，不再代表当前主机事实或开放计划。后续新增治理范围应基于 fresh inventory 另建垂直切片 issue，并继续满足独立验证、显式授权和回滚边界。
